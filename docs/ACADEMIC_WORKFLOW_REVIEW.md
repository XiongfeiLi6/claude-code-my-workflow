# Strengthen verification while simplifying project setup

Reviewed November 13, 2026. The owner subsequently approved incorporation; see [implementation status](#implementation-status) below. **Keep the existing academic workflow and improve a few specific checks.** The three researchers' materials largely reinforce capabilities already present in the Claude and Codex versions: durable project context, planning, source-grounded review, empirical audits, researcher understanding and explicit verification. The most immediate corrections are to preserve full PDF coverage by default and to describe precisely what formal proof verification establishes. The most useful next additions are concise checks for instruction conflicts, feasibility, actionable feedback and a successful pilot before batch work. None of the reviewed materials requires separate startup prompts for papers, proposals and lectures. A short generic prompt, complete repository copy and project-specific configuration fit the user's preferences; shared manuscript and exhibit rules remain authoritative. This report distinguishes source inspection and recommendations from implementation and runtime validation.

## Bäckman makes verification a research practice

Bäckman's guides connect persistent project instructions, reviewable changes and deliberate verification. They cover research and teaching across both Claude Code and Codex. Their practical implication is to preserve the intent of a procedure when moving between tools, rather than carrying over commands or tool names that the new runtime does not support. The user's complete-library approach is compatible with this: relevant procedures can be selected after the agent reads the project objective. ([AI guides](https://claesbackman.com/ai-guides.html), [Claude introduction](https://claesbackman.com/claude-code-guide.html), [Codex introduction](https://claesbackman.com/codex-vscode-guide.html))

His verification guide distinguishes several useful checks: fresh criticism of changes, review by another model, questions that test the researcher's understanding, and an independent implementation based on a specification that withholds original code and expected results. These checks address different errors. A different model can share the original's mistake; a reviewer can inherit the author's framing; an implementation can reproduce an ambiguous specification faithfully and still answer the wrong question. Reserve expensive independent replication for consequential results, and inspect sample construction, merges, distributions and correspondence between outputs and paper claims. ([Verification guide](https://claesbackman.com/verifying-llm-output.html))

The existing `audit-analysis`, `explain-diff`, `coauthor-brief` and review-fencing procedures already cover much of this. The explanation quiz should test empirical consequences and assumptions, rather than mere recognition of code. Review fencing should document what evidence the reviewer saw; a fresh conversation alone does not establish independent errors or a filesystem boundary. These are reasons to use the present procedures carefully, rather than add another mandatory reviewer to every task.

The workshops add useful teaching details. Test a new procedure on familiar material, inspect its mistakes, revise the responsible instruction, and try again in a fresh context. Synthetic data can exercise a pipeline but cannot establish the actual data's selection, dependence or missingness patterns. Rehearse generated presentations because producing the slides no longer guarantees that the speaker has practiced the argument. For teaching, decide what students must demonstrate unaided and what AI-assisted work should teach; ground feedback in the instructor's rubric and identifiable evidence. These are adaptable teaching practices, not universal assessment policies. ([Research workshop](https://claesbackman.com/ai_workshop/Session2_explorable/session2.html), [Teaching introduction](https://claesbackman.com/ai_workshop/teaching_session1.html), [Teaching exercises](https://claesbackman.com/ai_workshop/teaching_session2.html))

Preserve the user's single shared writing source. The workshop's example of extracting a project voice from prior writing need not produce another project-local style file. Likewise, an Overleaf synchronization recipe does not authorize overwriting a collaborator's edits or publishing. Local agent interfaces also do not make provider access to read files disappear. ([Research setup](https://claesbackman.com/ai_workshop/Session1_explorable/index.html), [Overleaf guide](https://claesbackman.com/overleaf-vscode-guide.html))

## Andrews prioritizes judgment and precise review

Andrews's April note encourages researchers to experiment with useful delegation while developing the expertise needed to evaluate it. Economic taste, engagement with real research questions and the ability to audit an answer remain central. Its observations about model capabilities are dated judgments, not a continuing benchmark. The existing defense questions and coauthor brief can support this goal: the researcher should be able to explain the substantive choices and recognize what remains unresolved. ([April 4 note](https://economics.mit.edu/sites/default/files/2026-04/IA%20AI%20note_3.pdf))

The August advisor materials offer a compact model for helpful feedback: organize around one or two governing issues; anchor comments precisely; propose feasible alternatives; distinguish necessary repairs from optional improvements; consider the delay and payoff of major requests. Check extraction gaps before alleging an omission. State what alternative diagnostic outcomes would mean before running the diagnostic. Draft the detailed comments before the overall assessment. These principles can improve existing review guidance without importing Andrews's personality, wording exemplars, word quotas or journal-outcome framing. The archive has no explicit license file identified in this review, so paraphrase and link the ideas rather than vendor its text. ([Advisor archive](https://economics.mit.edu/sites/default/files/2026-08/research-feedback-ia.zip))

The theory case study and companion files show why **verification needs a declared scope**. The paper describes an AI-assisted TSLS decision-theory investigation in a known-covariance Gaussian experiment, with limitations and separate computational checks. The Lean material distinguishes fully formalized statements from normalized-coordinate results, assumed representation objects and unformalized bridges. A successful build establishes a derivation under formal premises; it does not establish that those premises and definitions express the intended economic claim. Keep a map from formal statements to the manuscript, and disclose assumptions, axioms, dependencies and numerical work outside the prover. This review did not independently audit the mathematics. ([Case study](https://economics.mit.edu/sites/default/files/2026-10/AI%20Metrics%20Case%20Study_1.pdf), [Lean archive](https://economics.mit.edu/sites/default/files/2026-10/TSLS%20Lean%20Formalization.zip))

The certificate archive also illustrates a package-completeness issue. Static inspection found external modules and sibling inputs required by its verifier but not bundled there. Its saved summary contains `all_rules_pass: true` and `all_constants_match: false`. Those saved outputs are upstream evidence, not a successful rerun by this review. Existing replication-package guidance should retain that distinction: the presence of a verifier script and a saved log does not make an archive self-contained. ([Certificate archive](https://economics.mit.edu/sites/default/files/2026-10/TSLS_Certificate_Verification.zip))

## Matray supplies useful checks before scaling work

Matray's central cycle is natural-language specification, proportionate planning, feasibility review, execution and verification. Check required inputs, actual paths, coverage and assumptions before building an expensive pipeline. Inspect empirical outputs and changes rather than treating an agent's completion statement as evidence. His customization advice separates durable personal preferences from project configuration, records concrete lessons and checks for conflicting instructions. These ideas fit the existing project contract, memory and shared-style arrangement. ([Core workflow](https://adrienmatray-ai.com/core-workflow.html), [Customization](https://adrienmatray-ai.com/making-it-yours.html))

The clearest additional operational rule is **pilot before batch**. Start with one interactive unit, verify the output and then scale only work with clear inputs, outputs, bounds and stop conditions. Keep uncertain research judgments interactive. Large-data advice also supports explicit metadata—definitions, units, valid values, time coverage and source versions—and documented harmonization decisions. Parquet and DuckDB are optional tools when scale warrants them, not dependencies for every academic project. ([Async workflows](https://adrienmatray-ai.com/async-workflows.html), [Large datasets](https://adrienmatray-ai.com/large-datasets.html))

His failure examples reinforce existing checks for sample losses, merge outcomes, fabricated details, scope creep and silent data decisions. A small addition would ask reviewers to identify unexplained features and omitted evidence before accepting the preferred interpretation. It should not automatically launch new analyses or change approved scientific choices. Git guidance usefully distinguishes saving, committing and pushing, and favors distinct working copies for collaborators; claims about rapid recovery cannot guarantee recovery of uncommitted or unpushed work. ([Common failures](https://adrienmatray-ai.com/common-failures.html), [GitHub and Dropbox](https://adrienmatray-ai.com/github-dropbox.html))

**Do not bulk-import the public skills.** At the inspected revision, Matray's tree lacks several helpers required by its instructions: the PDF extractor, automated review-loop and harness files, and the Codex wrapper's fix-verification script. Other procedures include blanket staging, automatic stash/rebase, permission bypass or external model pipelines. These choices conflict with the current workflow's scoped permissions and the user's preference for the official Codex integration. Missing files are static completeness findings, not a claim that a runtime test failed. ([Repository tree](https://api.github.com/repos/amatray/claude-skills-public/git/trees/06ad26fb84434f48b4c5aeb19d3a67f743c0304d?recursive=1), [PDF skill](https://github.com/amatray/claude-skills-public/blob/06ad26fb84434f48b4c5aeb19d3a67f743c0304d/skills/pdf-chunker/SKILL.md), [Automated plan review](https://github.com/amatray/claude-skills-public/blob/06ad26fb84434f48b4c5aeb19d3a67f743c0304d/skills/review-plan-auto/SKILL.md), [Overleaf skill](https://github.com/amatray/claude-skills-public/blob/06ad26fb84434f48b4c5aeb19d3a67f743c0304d/skills/overleaf/SKILL.md))

## Improve existing procedures without growing the startup prompt

The following mapping is a maintenance proposal grounded in targeted comparisons, not a complete audit of every local skill. Claude skills live under `.claude/skills/`; their Codex counterparts live under `.agents/skills/`. Claude rules/references use `.claude/rules/` and `.claude/references/`; Codex uses `workflow/rules/` and `workflow/references/`.

| Treatment | Change in both versions | Placement and acceptance evidence |
|---|---|---|
| Requested maintenance | Git-fetch default, final private GitHub creation/push command, short generic starter, remove retired oil-oil setup instructions | `docs/START_HERE.md` and linked guides; inspect commands and preserve official integration and shared styles. Git-fetch retains template history. |
| Accuracy correction selected | Full PDF including references/appendices by default; explicitly requested main-text-only scope records omissions | `pdf-to-markdown/SKILL.md`; test full and trimmed paths and inspect extracted page coverage. |
| Accuracy correction selected | Clarify formal proof scope and remaining bridges | `references/theory-proving.md`; remove unconditional trust language and require assumptions and manuscript mapping. |
| Already covered | Citation support, empirical audits, researcher quizzes, continuity and review fencing | Reuse `verify-claims`, `validate-bib`, `audit-analysis`, `explain-diff`, `coauthor-brief`, checkpoints and review rules. |
| Proposed priority 1 | Check configuration conflicts after instruction edits | Extend configuration maintenance/context audit: compare global/project instructions, shared style and dated decisions; resolve precedence explicitly. |
| Proposed priority 1 | Check feasibility and feedback usefulness | Extend planning/review guidance with required inputs, real coverage, crux, anchored evidence, feasible repair, payoff and optionality. |
| Proposed priority 2 | Pilot before bounded batches | Extend orchestration beyond review fan-outs; declare resources, stop conditions and success evidence before scaling. |
| Proposed priority 2 | Inspect surprising output before interpretation | Add one focused check to audit/diagnose/exhibit review; proposed scientific changes still need owner decisions. |
| Optional reference | Teaching rubric evidence and learning objectives; metadata/harmonization; collaborator working copies | Extend existing syllabus/exercise or data references only when relevant. Keep student-data handling and actual build tools project-specific. |

The two accuracy corrections are selected for the current maintenance work; the broader recommendations remain proposals. Actual validation, commit and push status belongs in the maintenance completion record, not in this source review. The next useful experiment is small: try the concise advising checklist or batch-pilot contract on a familiar task, record which substantive mistake it prevented, and retain only the instruction that earned its place. This keeps the entry prompt short while making the durable workflow more dependable.

## Implementation status

Following owner approval, both workflows now incorporate the previously proposed
checks through existing procedures: context-audit for instruction conflicts and
evidence-based cleanup; planning for feasibility; orchestration for batch pilots;
review-paper and review orchestration for actionable feedback; audit-analysis and
diagnose for unexpected outputs. Pedagogy-review routes to teaching objectives and
data-analysis routes to data harmonization references when relevant. No new skill
or automated hook was added, and the starter prompt and shared styles are unchanged.

The proposal table above records the review-stage recommendations. This section
records their subsequent adoption. Existing runtime/schema gates and isolated
scenario checks are used for validation; these are not evidence of improved research
outcomes across live projects. Future usage should determine whether to refine or
remove instructions that do not help.
